## Hard Rules (TypeScript / Svelte / SQL)

* **Svelte 5 runes mode is forced project-wide** (vite.config.ts) — `$props()`, `$state()`, `$derived()`; no legacy `export let`/`$:` reactivity. Kit options live in `vite.config.ts` (there is no svelte.config.js).
* **Engine modules take `db: DB` as a parameter** (`src/lib/server/db/type.ts` — based on `BaseSQLiteDatabase` so transaction handles qualify). Only routes/auth/scheduler import the app singleton. This is what makes the in-memory test DB work — don't break it.
* **Engine modules stay pure Node** — no `$env`, `$app`, or SvelteKit imports in `src/lib/server/*` engine code (auth.ts is the exception and is not unit-tested). `db/index.ts` reads `process.env` directly so seed/scripts/tests can share it.
* **Dates are `YYYY-MM-DD` local-calendar strings** everywhere (due dates, start dates). Arithmetic goes through `src/lib/server/dates.ts` (UTC internally). **Never** use `toISOString().slice(0,10)` for "today" — that's UTC and breaks near midnight; use `todayLocal()` (server) / `toLocaleDateString('en-CA')` (scripts).
* **Money is integer cents** (`weekly_allowance_cents`, `amountCents`); dollars exist only at the form boundary. Weekday masks: bit 0 = Monday … bit 6 = Sunday.
* **MONEY PRIVACY IS LAW.** No kid may ever see another kid's earnings, balance, ceiling, or day count — and the week's divisor is rendered as a bare number, NEVER attributed to whoever set it. Adults see everything. Every new money surface gets checked against this before it ships; `computeHouseholdWeek` returns the whole family by design, so any kid-facing caller MUST pick out that kid's entry and send only that to the browser.
* **Frozen at the right moment, three different moments:** `weight`/`isBonus` are stamped when the INSTANCE IS CREATED (retuning a chore's points mid-week must not move the denominator under a week in progress); `pointsAwarded` is stamped at VERIFICATION; `payoutCents` is stamped at SETTLEMENT (what a chore paid isn't knowable until the week it lives in is divided up). Nothing recomputes afterwards.
* **The allowance ledger is append-only** and now only ever written by settlement, bonuses/penalties, and payouts — never per chore. Balance = SUM(amount_cents).
* **A settled week is frozen.** `assertWeekOpen` blocks markDone/undo/verify/reject/remind/bonus on any instance whose week has a `weekly_settlements` row: the money on record must keep matching the chores on record. Adults correct a settled week with a bonus.
* **Schema changes:** edit `src/lib/server/db/schema.ts`, then `npx drizzle-kit generate --name <slug>`. Never hand-edit generated SQL in `drizzle/` or its `meta/` snapshots. Migrations auto-apply on boot (`hooks.server.ts`, skipped during build).
* **better-sqlite3 is synchronous:** `.all()`/`.get()`/`.run()`, and insert-returning is `.returning().get()` (bare destructuring type-errors). `.run().changes` is how generation detects real inserts.
* **Transactions roll back on throw** — a status write that must survive an intentional throw goes OUTSIDE the transaction (see `acceptSwap`; this bug shipped once already).
* **Validation is zod at the route boundary** (`validation.ts`); services throw `InstanceActionError` with user-facing messages and routes surface them via `fail(400)`.

## Core Architecture

* **Stack:** SvelteKit 2 (Svelte 5, adapter-node) + Tailwind v4 (`@tailwindcss/vite`, no config file) + Drizzle ORM on better-sqlite3 (WAL, FKs on) + node-cron. One app, one SQLite file (`data/chores.db`), photos in `data/uploads/`.
* **Rooms & chore library:** `rooms` table + nullable `chores.room_id` (null = "General") + `chores.icon`. Rooms are purely organizational — generation/rotation/payout never read them; `deleteRoom` releases its chores to General. The built-in catalog ships as CODE (`src/lib/choreLibrary.ts`), never as DB rows — a fresh household starts empty. `library.ts` multi-adds templates UNASSIGNED and skips titles already in the room. Templates carry NO points and no money — weight defaults from frequency (`DEFAULT_POINTS` in `src/lib/points.ts`: daily 1, weekly 3, monthly 5, yearly 7) so hand-made and library chores share one scale; mixing scales would let library chores dominate a day's split. Unassigned chores are legal everywhere (generation skips them — that's the "stock the house first, assign later" flow). Person-centric assignment lives in `assignments.ts` (fixed = replace assignee, rotating = append to pool; both drop future pending + regenerate). `/admin/chores/new` uses NAMED actions (`?/custom`, `?/library`) — SvelteKit forbids mixing default + named.
* **Chore vs ChoreInstance is the backbone:** a Chore is the recurring definition; a ChoreInstance is one dated occurrence (status `pending|done|verified|rejected|skipped|missed`) and carries reminder count, frozen payout/points, photo. `UNIQUE(chore_id, due_date)` is the idempotent-generation guard.
* **Generation (`generate.ts`):** rolling 14-day window for daily/weekly (`ROLLING_WINDOW_DAYS`), next-occurrence-only for monthly/yearly. Insert-or-ignore. Runs nightly 00:05 + on boot (`scheduler.ts`, HMR-guarded via globalThis; the cron task is destroyed on `sveltekit:shutdown` or Ctrl+C hangs — do not remove that handler).
* **Rotation is DERIVED, never stored (`rotation.ts`):** `pickRotationAssignee` is a pure function — among pool members home on the due date, the turn goes to whoever has gone longest without that chore (never-served first, ties by pool position), counting only turns dated strictly BEFORE the day being filled. The old `chore_rotation_state` pointer was dropped (migration `0008`) because a pointer cannot express away-day fairness: it moved to whoever covered, silently eating the away person's turn. Derived means idempotent — every delete-and-regenerate path re-derives the same schedule, so a rebuild only moves the days the change actually affected. **Anything that alters presence or pool membership must tear down the whole FORWARD window of the affected rotations**, not just the freed day (`applyPresenceChange` → `rebuildRotations`): the window is materialized ahead, so a one-day backfill leaves later turns laid out as if nobody had left. Instances carrying an open swap request are exempt from the teardown — deleting them cascades the request away.
* **Sweep (`sweep.ts`):** pending past `due_date + grace_days` → `missed` (visible, no payout, can't be completed).
* **Presence (`presence.ts` reads / `presenceAdmin.ts` mutations — split to avoid a generate↔presence import cycle):** per-person home/away. Resolution: day override → newest matching rule (weekly / biweekly-with-anchor / monthly, clamped) → default HOME. Weekly rules carry a **weekday mask** (bit 0 = Monday; one rule = "away weekdays"/"weekends"/any set); rows with mask 0 are legacy and fall back to their single `weekday` — never backfill, the code handles both. **Day overrides are self-cleaning:** `toggleDay` deletes the override when the flipped value matches what rules alone would say (click-click returns a day to pattern-following instead of pinning it); `clearFutureOverrides` drops today-onward overrides. The calendar's *planned* overlay is presence-aware like generation: fixed chores skip the assignee's away days, rotation TBDs vanish only when the whole pool is away. Generation never schedules an away (or deactivated) person; rotations hand the turn to the next member who IS home; every presence mutation runs `applyPresenceChange` (drops the person's future PENDING instances on away days — freeing the unique chore+date slot for rotation backfill — then regenerates). Streaks are naturally unaffected (away days have no instances). Swap requests refuse targets who are away on the due date.
* **Weekly allowance (`allowance.ts`) — the money model.** ONE household pot per week (`weekly_allowance_cents`); everyone can earn the same, and what separates two kids is only how many days they were around to work.
  * `fullWeekDays` (D) = the busiest kid's chore-day count, or a pinned `full_week_days` override. Only KIDS count — an adult in a rotation pool must not set the household's bar.
  * `dayValue = pot / D` (identical for everyone) → `ceiling(k) = daysWorked(k) × dayValue`. Away days generate no instances, so they silently shrink the ceiling — gone all week means nothing assigned and nothing owed.
  * Inside a day, the day's value splits by weight: `earned(i) = dayValue × weight(i)/dayWeight × reminderFactor(i)`. **A day pays the same whether it holds one chore or five** — that's deliberate, it rewards finishing your day; points only decide how a day splits internally.
  * `reminderFactor` (`payout.ts`): 0 reminders = 1, 1 = `(100-penalty)/100`, 2+ = 0. It scales WEIGHT now, not cents.
  * Missed/rejected stay in the denominator (the whole point); `skipped` is excluded (an adult saying "not needed" mustn't cost anyone).
  * **Compute in fractional cents and round ONCE at the end** — a kid who did everything must see exactly $10.00, not $9.98 of drift. `lostCents` is derived from the rounded figures so the three always add up to the ceiling on screen.
  * Bonuses (`chores.is_bonus` instances + adult-granted `chore_instances.bonus_points`) sit OUTSIDE the denominator and pay at the flat week-average rate `pot × points / weekAssignedWeight` — so a bonus is worth the same whichever day it lands on and can't be farmed by saving it for a light day. Uncapped. A kid with nothing assigned borrows the busiest kid's week weight for the rate.
* **Settlement (`settleDueWeeks`, nightly + on boot):** a week closes and pays `settlement_grace_days` (default 1) after it ends, so the weekend verify queue still counts. Writes ONE `earning` ledger row per kid plus a `weekly_settlements` row — `UNIQUE(user_id, week_start)` is the double-pay guard, since the cron re-runs. Catches up after downtime, bounded to `MAX_RETRO_WEEKS` (8) so switching the allowance on doesn't retroactively pay out the whole history. **Order matters in `scheduler.ts`: sweep BEFORE settle**, or unfinished chores still look open and get counted as "still winnable" at the moment the week is closed.
* **Point goals (`goals.ts`):** adult-set targets per kid or family-wide, daily or weekly. They count RAW points from verified instances — undiscounted by reminders, because money is already the stick. No money involvement at all; the reward is a text note. `goal_achievements` has `UNIQUE(goal_id, period_start)` so a celebration fires exactly once. **Claiming happens in a POST action, never in `load`** — a speculative link preload runs `load`, so claiming there lets a hover-and-move-away swallow the celebration.
* **Lifecycle (`instances.ts`):** markDone (assignee or adult; photo required if `requiresPhoto`; auto-finalizes when `!requiresVerification`) → verify/reject (adult) → ledger. Undo: `done` reverts any time; auto-verified reverts within `undo_window_minutes` (unwinds ledger + payout); adult-verified never undoes (reject instead).
* **Auth (`auth.ts`):** profile picker + argon2 PIN; sessions stored as sha256(token), 90-day sliding expiry. Cookies are `secure: false` **by design** (plain-HTTP LAN — browsers drop Secure cookies there). `requireUser`/`requireAdult` guard every load/action; `hooks.server.ts` populates `locals.user`.
* **CSRF is OURS, not kit's:** `csrf.checkOrigin: false` in vite.config.ts (kit's check needs one fixed ORIGIN, and without ORIGIN adapter-node assumes **https**, 403ing every plain-HTTP form post). `hooks.server.ts` enforces the equivalent same-host check (Origin header host === Host header) so localhost, the LAN IP, and a hostname all work at once while cross-site posts still 403. **Do not set ORIGIN** for LAN deployments; it would re-pin to a single address. (`checkOrigin` is deprecated upstream in favor of `trustedOrigins`, which can't express same-host — revisit if it's removed.)
* **Settings (`settings.ts`):** key/value `app_settings` with `DEFAULT_SETTINGS` (currency symbol, penalty %, undo window, week start, weekly allowance, full-week days, settlement grace, backup count) + the auto-generated VAPID keypair. Currency threads from the root layout load into every `formatCents` call. **`week_start` is any weekday name** ('monday'…'sunday', default `saturday`) — it drives the calendar, the leaderboard AND the allowance week. `startOfWeek`/`endOfWeek` take a name or an index; `weekdayIndex()` converts. Pages that lay out a month grid rotate their header labels and leading blanks by that index.
* **Push (`push.ts`):** zero-config VAPID (generated into app_settings). `notifyUser` is fire-and-forget — it must never block or fail an action; 404/410 prunes the subscription. Browsers require a secure context (HTTPS or localhost) to subscribe — same caveat as PWA install; the UI hides itself elsewhere.
* **Swaps (`swaps.ts`):** one open request per instance; accept reassigns just that occurrence (rotation state untouched); accepting a no-longer-open chore auto-cancels the request.
* **Photos (`uploads.ts` + `/photos/[name]`):** stored under `data/uploads` with generated names; `PHOTO_NAME_RE` is the path-traversal guard on the auth-gated serving route — keep every photo path through it. Undo/reject delete the file. `BODY_SIZE_LIMIT=10M` required in prod (adapter default 512kb rejects phone photos).
* **Backup/restore (`zipLite.ts` + `/admin/backup`):** download = consistent snapshot via better-sqlite3's online `backup()` + photos, zipped (store-method, dependency-free). Restore validates integrity + the `__drizzle_migrations` table, snapshots live data to `.pre-restore`, restores INTO the running app via the backup API, then re-runs migrations. zipLite writes STORE only, reads STORE + DEFLATE.
* **Calendar:** materialized instances + computed future occurrences from recurrence rules ("planned", rotations shown as TBD). Honors the week-start setting.
* **Family board (`/board`):** kiosk view for a wall tablet — everyone's day, progress, streaks; auto-refreshes every 60s (paused while the PIN overlay is open) with a live clock. Renders chrome-less (the layout hides header + bottom nav on `/board`). Tapping a person opens a PIN overlay whose `?/switch` action mints a REAL session (same verification as login) so doneBy/audit attribution stays honest. Any logged-in user can view; balances deliberately not shown. **Leaving always costs a PIN:** "exit board" opens the opener's own PIN overlay, and 🔒 Lock swaps the session for a `kind='kiosk'` session (sessions.kind, migration `0007`) that can ONLY see /board — `requireUser` bounces kiosk sessions there, so typed URLs dead-end. `?/switch` (PIN) is the only way out; board load/actions must NOT use `requireUser` (they'd loop) — they check `locals.user` directly. **A switch FROM a locked board mints a `kiosk_visit` session** (no migration — `kind` is plain TEXT, the enum is type-level only): full access for that person, 24h expiry (sliding renewal is per-kind — renewing a visit with the 90-day span would make it permanent), and the layout swaps Log out for a "📺 Back to board" button posting `?/lock` (relocking never needs a PIN) plus a 3-minute idle auto-return. Set-and-forget: the tablet always ends up back at the locked board.
* **Streaks/points (`stats.ts`):** streak = consecutive *due-days* fully completed, walking back from today; empty days skip, in-progress today neither counts nor breaks. Points sum `pointsAwarded` on verified instances only.

## Do-Not-Relearn Gotchas

* WV2/Access lessons do NOT apply here — this is a plain Node/SvelteKit app.
* `vite build` must never touch a database: boot-time work is gated on `!building` in hooks.
* Vitest uses its own `vitest.config.ts` (with the `$lib` alias) — it deliberately does NOT load the SvelteKit vite config.
* The scaffold-era `state_referenced_locally` warnings are silenced with `svelte-ignore` comments where the initial-value capture is intentional (form initials, login selection) — don't "fix" those into deriveds.
* `npm audit` shows ~8 vulns living entirely in drizzle-kit's bundled dev-time deps (`@esbuild-kit/*`) — known, not runtime, don't `audit fix --force`.
* Node 24 on the dev box; Docker NOT installed (don't try to run it). Dockerfile pins `node:22-alpine` (Vite 8 needs ≥20.19/22.12 — the plan's original Node 20 floor is stale).

## Run / Deploy

* Dev: `npm run dev` (localhost:5173). Prod-local: `npm run build` then `node build` (port 3000; Ctrl+C exits cleanly). Phone-on-LAN dev: `npm run dev -- --host`.
